# ProspEl — Подробное описание работы программы

## Версия 3.0

- **Income:** `issued_date` (alias колонки `date`), `status` (issued|partial|paid|cancelled), `project_id`, `income_type` (advance|intermediate|final|other). Старые записи: status='paid' если paid_date есть, иначе 'issued'.
- **Expenses:** `paid_date`, `status` (planned|paid|reversed), `is_tax_related`, `source` (manual|planned|obligation|bank_import|efaktura_import|cash_transfer), `reversed_expense_id`, `reversal_of_id` — сторно вместо удаления.
- **Projects:** статусы (lead|active|completed|archived), связь с доходами, расходами, договорами.
- **CashEntry:** учёт наличных средств, связь с банковскими транзакциями (снятия) и расходами.
- **State Machine:** централизованный модуль (`backend/state_machine.py`) для контроля переходов статусов Income, Expense, MonthlyObligation, Project.
- **period_closures:** таблица для закрытия периодов (year, month, closed_at, closed_by_user_id).
- **Запрет удаления:** расходы из obligation и bank_import не удаляются физически — создаётся сторно (reversal).

## 1. Общие сведения

**ProspEl** — бухгалтерская система для индивидуального предпринимателя (ИП) на паушальном режиме налогообложения в Республике Сербия. Программа ведёт учёт доходов, расходов, обязательных платежей (налоги и взносы), планируемых расходов, проектов, кассы и предоставляет отчёты в формате, соответствующем требованиям Пореске управе (налоговая служба Сербии).

### Архитектура

- **Backend:** FastAPI (Python 3.10+), асинхронная работа с БД через SQLAlchemy
- **Frontend:** React (Vite), SPA-интерфейс
- **База данных:** SQLite по умолчанию (aiosqlite), возможна замена на PostgreSQL
- **Аутентификация:** JWT-токены, bcrypt для хеширования паролей
- **Бэкап:** автоматические snapshots SQLite с расписанием и ручное управление через UI
- **State Machine:** `backend/state_machine.py` — централизованный контроль переходов статусов

### Разработка: линт и тесты

Dev-зависимости бэкенда: `pip install -r requirements-dev.txt` (в venv).

Проверки (эти же шаги гоняет CI, все должны быть зелёными):

```

ruff format --check backend alembic run.py create_admin.py # проверка форматирования

python -m alembic upgrade head                     # применить миграции БД

# Frontend (из папки frontend)
npm run lint          # ESLint, --max-warnings=0: предупреждения тоже валят проверку
npm run format:check  # проверка форматирования Prettier
npm run build         # проверка сборки
```

Автоформатирование (запускать перед коммитом, если проверки красные):

```

```

CI (GitHub Actions, `.github/workflows/ci.yml`) гоняет всё это на каждый push/PR в main. ESLint работает в режиме zero-warnings: существующие осознанные исключения помечены `eslint-disable-next-line` в коде, любое новое предупреждение валит CI.

### Миграции БД (Alembic)

Схема БД управляется Alembic. Приложение больше не создаёт и не меняет таблицы при старте.

Новая пустая база:

```bash
python -m alembic upgrade head
```

Существующая база, которая была создана старыми ручными миграциями, один раз ставится на учёт и выравнивается:

```bash
python -m alembic stamp 20260705_0001
python -m alembic upgrade head
python -m alembic current
```

`20260705_0002` чистит legacy-дрейф SQLite-схемы: переносит старые `cash_transactions` в `audit_logs`, удаляет Windows-only legacy-остатки и добавляет недостающие индексы. После этого все будущие обновления схемы выполняются обычной командой:

```bash
python -m alembic upgrade head
```

Новая миграция после изменения `backend/models.py`:

```bash
python -m alembic revision --autogenerate -m "описание изменения"
python -m alembic upgrade head
```

### Безопасность запуска (APP_ENV)

- `APP_ENV=dev` (по умолчанию) — создаётся admin/admin при первом запуске, используется дефолтный SECRET_KEY, CORS разрешён для localhost
- `APP_ENV=prod` — admin/admin НЕ создаётся, SECRET_KEY обязателен (мин. 32 символа, не дефолтный), CORS_ALLOWED_ORIGINS обязательно задан (wildcard `*` запрещён)

## 3. Аутентификация и пользователи

### Роли

- **admin** — полный доступ, управление пользователями и предприятием
- **accountant** — бухгалтер, полный учётный доступ
- **cashier** — кассир
- **observer** — только просмотр

В `dev` режиме при первом запуске создаётся пользователь `admin` / `admin`.
В `prod` режиме автоматическое создание пользователя отключено.

### Авторизация

- Вход по логину и паролю, получение JWT
- Токен сохраняется в localStorage, передаётся в заголовке `Authorization`
- Для защищённых маршрутов требуется валидный токен

## 4. Главная панель (Dashboard)

На панели отображаются:

1. **Баланс за месяц** — разница между доходами и расходами за текущий месяц
2. **Баланс за год** — то же за календарный год
3. **Баланс за всё время** — разница банковских приходов и расходов (с финансовым результатом)
4. **Планируемые расходы до конца месяца** — сумма планируемых и обязательных платежей с дедлайном до конца текущего месяца
5. **Круговые диаграммы** — соотношение доходов и расходов за месяц и за год
6. **Лимиты паушального режима:**
   - 6 млн RSD в год — превышение влечёт переход на общий режим
   - 8 млн RSD за 12 месяцев — превышение требует регистрации НДС
7. **Предупреждение о платежах** — список просроченных и приближающихся обязательных платежей (налоги, взносы)
8. **Последние доходы** — таблица недавних записей КПО (без отменённых)

## 5. Доходы (Книга прихода и расхода — КПО)

- Записи с датой, номером счёта, клиентом, описанием, суммой
- Позиции фактуры (`income_items`): сумма дохода считается из строк, подсказки позиций из прошлых фактур и договоров
- Контрагент выбирается только из справочника; проекты в форме ограничены выбранным клиентом и `Razno`
- Связь с договором, проектом и типом платежа (аванс, промежуточный, закрывающий)
- Генерация следующего номера счёта (формат `YYYY-NNNN`)
- Предупреждение о дублировании номера счёта
- Ручные платежи и автоматическая сверка через банковское сопоставление (включая частичные оплаты через аллокации)
- Статусы: `issued` → `partial` → `paid`, `issued/partial` → `cancelled`
- Экспорт в **CSV** и **PDF** для отчётности; экспорт исходящей фактуры в **eFaktura UBL XML** (non-VAT для паушала)

---

## 6. eFaktura

- Импорт XML-файлов электронных счетов
- Синхронизация с eFaktura API (входящие и исходящие документы); настройки в `Настройки / eFaktura API`
- Автоматическое создание записей доходов и расходов из eFaktura
- Исходящие фактуры со статусами `Storno`/`Cancelled`/`Mistake` не создаются как доход; уже импортированный доход по сторнированной фактуре отменяется при синхронизации, если по нему нет оплат
- PDF на сервере не хранятся: при включённой опции frontend скачивает PDF на компьютер пользователя
- Связь с клиентами по PIB

## 7. Клиенты

- Хранение: название, адрес, PIB (налоговый номер), контакт, тип (юр. лицо / физ. лицо)
- Архивация (деактивация без удаления)
- Поиск по названию и параметрам

## 8. Проекты

- Центры учёта для группировки доходов и расходов
- Статусы: `lead` → `active` → `completed` → `archived`; `lead` → `archived` (для «мёртвых» лидов)
- Внутренние проекты: `INT-UNASSIGNED`, `INT-SALARY`, `INT-CASH` (создаются автоматически)
- Связь с договорами, доходами и расходами

---

## 9. Договоры

- Номер, дата, клиент, предмет, сумма, сроки действия
- Типы: услуги, поставка, аренда, комиссия
- Позиции договора: описание, количество, цена
- Статусы: активен, завершён, расторгнут
- Связь с доходами — при создании дохода можно указать договор и тип платежа
- Автоматическое создание проекта при создании договора (если не указан)

---

## 10. Расходы

- Дата, описание, сумма, категория (материалы, услуги, аренда, прочее, налог, zarade)
- Статусы: `planned` → `paid` → `reversed` (через сторно)
- Фильтрация по году и месяцу, поиск, сортировка
- Экспорт в CSV
- Обнаружение и слияние дубликатов
- Автоматическое создание записей при:
  - оплате планируемого расхода
  - оплате обязательного платежа (налог, PIO и т.д.)
  - импорте банковской выписки
  - импорте eFaktura
- Расходы с `source=cash_transfer` скрыты в общем списке расходов (отображаются только в Кассе)

### Сторно (Reversal)

- **PATCH /api/expenses/{id}/reverse** — явное сторно расхода
- Создаётся запись с `amount = -original.amount`, `status=reversed`, `reversal_of_id=original.id`
- Оригинал остаётся `status=paid`, получает `reversed_expense_id`
- **DELETE /expenses/{id}** — всегда создаётся сторно, физическое удаление отсутствует
- Отчёты: `sum(Expense.amount)` учитывает сторно (отрицательные суммы)

## 11. Планируемые расходы

Периодические расходы с настраиваемым периодом:

- **Периоды:** еженедельно, ежемесячно, ежеквартально, ежегодно
- **Параметры:** день уплаты, даты начала/окончания, напоминание
- **Категории:** аренда, интернет, телефон, коммуналка, страхование, ПО, прочее

### Предстоящие платежи

- Список планируемых платежей на выбранный период (30, 60 или 90 дней)
- Для каждого платежа: отметить «оплачено» (создаётся запись в Расходах) или отменить оплату (применяется сторно)

---

## 12. Банковские транзакции

- Просмотр импортированных транзакций из банковской выписки
- Сопоставление (match) с доходами, расходами, обязательствами
- Категория «Наличка» — автоматическое создание записи в Кассе при сопоставлении
- Статусы: `unmatched`, `matched`, `ignored`
- Отвязка (unmatch) с автоматической синхронизацией статусов связанных сущностей

---

## 13. Касса (наличные)

- Реестр наличных средств: снятия из банкомата и расходы наличными
- Пополнение кассы: привязка к банковскому снятию (cash_transfer)
- Расходы из кассы: отображаются и в кассе, и в общем списке расходов
- Баланс кассы: может уходить в минус
- Поиск и сортировка
- Редактирование записей

---

## 14. Налоги и взносы

Модуль обязательных платежей Пореске управе (налоговая служба Сербии).

### Типы платежей

- **Порез на приход** — налог на доход
- **PIO** — допринос за ПИО (пенсионное страхование)
- **Здравствено осигурање** — медицинское страхование
- **Незапосленост** — страхование на случай безработицы

### Решения (YearDecision)

Для каждого года и типа платежа задаются:

- Период (начало–конец)
- Месячная сумма
- Реквизиты: рачун примаоца, шифра плаћања, модель, позив на број
- Сврха уплате (шаблон с подстановкой года)
- Флаг «привремене аконтације» (предварительные взносы)

### Календарь обязательств

- Для каждого месяца создаются обязательства (MonthlyObligation) на основе решений
- **Дедлайн** — строго 15-е число месяца, следующего за отчётным
- Статусы: `unpaid`, `overdue`, `paid`

### Операции

- **Отметить оплаченным** — ввод даты оплаты и номера платёжного поручения; автоматически создаётся запись в Расходах
- **Отменить отметку** — обязательство снова становится неоплаченным; применяется сторно связанного расхода
- **Автоматическое сопоставление** — исходящие банковские транзакции автоматически предлагаются для сопоставления с неоплаченными обязательствами
- **IPS QR** — данные для генерации QR-кода по стандарту NBS (Национална банка Србије)

## 15. Входящие фактуры

- Входящие фактуры поставщиков (импорт из eFaktura и ручные)
- Закрытие банком, наличкой или взаимозачётом; settlement идёт только через сервис (`incoming_invoice_settlements`), не прямой записью в таблицу
- Статус пересчитывается по `settled_amount` (не оплачено / частично / оплачено)
- Детальная модалка: summary-блок с действиями, связанные расход и банковская транзакция

## 16. Кассовые чеки

- Импорт чека по QR URL с `suf.purs.gov.rs` (вручную или из Android-приложения `android-app/`)
- Сохраняются ссылка на оригинал чека и позиции чека
- Создание расхода из чека и ручная привязка чека к существующему расходу
- Наличный чек: создаётся `Expense(source="cash", status="paid")` и `CashEntry(direction="out")`; ошибочную отметку «наличными» можно вернуть в ожидание банка
- Поиск по суммам, проекту, продавцу, ПИБ, адресу, номеру, способу оплаты, статусу, id связанных сущностей

## 17. Работники и выплаты

- Постоянные и временные работники; схемы оплаты: за выход, еженедельно, раз в месяц
- Ставка фактурирования работника (`billing_hourly_rate`) — для расчёта сумм к фактурированию в дневниках работ
- Типы выплат: обычная, еженедельная, месячная, аванс за командировку, окончательный расчёт командировки
- Командировки: дни и ночи считаются по датам, гостиница = стоимость ночи × количество ночей; окончательный расчёт предзаполняется из аванса
- Редактирование выплаты из реестра налички открывает форму выплаты

## 18. Дневники работ

- Аналитика работ: записи по проекту, бригаде (несколько работников, many-to-many) и датам; деньги за материалы живут в модуле Расходы
- Человеко-часы = длительность смены × число исполнителей; сверхурочные после 8 часов, коэффициент в настройках предприятия (по умолчанию 1.26 — Закон о раде РС)
- Надбавки: дневница и питание — на человека, проживание — на бригаду
- Материалы: `stock` (со склада, оценка) или `expense` (привязка к расходу того же проекта — не задваивается в затратах)
- Вкладка «Затраты по объекту»: расходы проекта + труд + надбавки + материалы со склада
- Печатные формы: `Грађевински дневник` и `Евиденција радних сати и утрошеног материјала`

## 19. Займы контрагентов

- Отдельные сущности `counterparty_loans` и `counterparty_loan_movements`
- Тело займа не создаёт Income/Expense и не попадает в P&L; в cash flow отражается как финансирование
- Банковская строка связывается с движением займа через `matched_type = "loan_movement"`
- Собственные средства — отдельная read-only секция из транзакций с `matched_type = "owner_funds"`

## 20. Финансовый сервис

- **GET /api/finance/summary** — агрегатор метрик accrual/cash (revenue, expenses, taxes, net profit)
- **GET /api/finance/pnl** — отчёт о прибылях и убытках
- **GET /api/finance/cashflow** — денежный поток
- **GET /api/finance/ar** — дебиторская задолженность: неоплаченные доходы
- **GET /api/finance/limits** — лимиты паушального режима

## 21. Настройки

### Предприятие

- Название, адрес, PIB, матични број, банковские реквизиты, шифра делатности

### Пользователи (только для admin)

- Добавление, редактирование, деактивация пользователей
- Роли, язык по умолчанию
- Нельзя деактивировать себя

### Категории расходов

## 22. State Machine (Централизованный контроль статусов)

Модуль `backend/state_machine.py` управляет всеми переходами статусов:

| Модель | Статусы | Ключевые переходы |
|--------|---------|-------------------|
| Income | issued, partial, paid, cancelled | issued → partial/paid/cancelled, partial → paid/cancelled |
| Expense | planned, paid, reversed | planned → paid, paid → reversed (через сторно) |
| MonthlyObligation | unpaid, overdue, paid | unpaid → paid/overdue, overdue → paid |
| Project | lead, active, completed, archived | lead → active/archived, active → completed/archived, completed → archived |

Все смены статусов проходят через сервисные функции state_machine. Прямое присвоение `status` в роутерах запрещено.

## 23. Доменные инварианты

- Кассовый чек сам по себе — документ подтверждения расхода
- Чек оплачен картой → связанный расход может быть `planned/waiting_bank` до появления банковской транзакции
- Чек оплачен наличкой → расход `Expense(source="cash", status="paid")` с `cash_entry_id`; ошибочный cash-mark удаляет только связанную `CashEntry` и возвращает расход в `planned`
- Банковские списания и расходы сравниваются по абсолютной сумме: `abs(bank.amount) == expense.amount`
- Проект чека и связанного расхода должен совпадать; смена проекта расхода переносится на чек
- Если в форме дохода/расхода выбран договор — проект подставляется из договора
- Тело займа не является доходом/расходом
- Снятия налички не матчатся автоматически на странице банка: дата проводки в выписке может отличаться от даты снятия, автозакрытие временных пополнений опасно; для снятий используется проект `_Gotovina / Наличка`
- UI-лейблы не хранятся как бизнес-данные: backend хранит код/тип, frontend переводит
- Привязанные к расходам материалы дневника работ не прибавляются к затратам объекта повторно
