# План реализации: займы и возвраты контрагентам

## Цель

Добавить учёт денежных займов с контрагентами так, чтобы тело займа:

- не попадало в доходы, расходы, P&L и показатели операционной прибыли;
- отражалось в банковских движениях и остатке денег;
- формировало отдельную дебиторскую или кредиторскую задолженность контрагента;
- поддерживало частичные возвраты, несколько траншей и исправление ошибочной привязки.

Пример исходного сценария: входящая банковская операция `+350 000 RSD` с назначением `Pozajmica ...` должна оформляться как получение займа от контрагента, а не как доход или внесение собственных средств.

## Архитектурное решение

Не использовать для займа `Income`, `Expense` или `IncomingInvoice`. Эти сущности участвуют в выручке, расходах либо расчётах по фактурам, поэтому заём исказит отчётность.

Не расширять смысл `owner_funds` до займов организаций. Текущая функция «Внести собственные средства» хранит только классификацию строки банка (`matched_type = "owner_funds"`) без контрагента, договора, остатка долга и погашений. Её можно использовать как UX-образец недоходной операции, но не как модель данных.

Реализовать отдельный реестр займов:

- `CounterpartyLoan` — карточка договора/долга;
- `CounterpartyLoanMovement` — выдача/получение денег и возвраты;
- банковская строка связывается с конкретным движением через новый `matched_type = "loan_movement"`.

Первая версия учитывает только тело займа. Проценты, комиссии и курсовые разницы требуют отдельных доходных/расходных операций и не должны смешиваться с principal.

## Поддерживаемые операции

| Сценарий | Тип займа | Направление банка | Движение займа | Влияние на задолженность | Не создавать |
| --- | --- | --- | --- | --- | --- |
| Мы получили деньги в долг | `borrowed` | `in` | `disbursement` | Увеличить кредиторку | `Income` |
| Мы вернули полученный долг | `borrowed` | `out` | `repayment` | Уменьшить кредиторку | `Expense` |
| Мы выдали деньги в долг | `issued` | `out` | `disbursement` | Увеличить дебиторку | `Expense` |
| Нам вернули выданный долг | `issued` | `in` | `repayment` | Уменьшить дебиторку | `Income` |

Остаток открытого тела займа для обоих типов:

```text
outstanding_amount = sum(disbursement) - sum(repayment)
```

Для `borrowed` этот остаток входит в обязательства перед контрагентом. Для `issued` он входит в требования к контрагенту.

## Текущее состояние кода

Перед реализацией учитывать уже существующие точки интеграции:

- `backend/models.py`: `BankTransaction.matched_type` и `matched_id` являются общей связью банковской операции с объектом учёта.
- `backend/bank_matching_service.py`: `MATCH_TYPE_OWNER_FUNDS` только помечает транзакцию; `unmatch_transaction()` содержит отдельную обработку каждого типа связи.
- `backend/routers/bank_transactions_router.py`: есть endpoint `POST /bank-transactions/{tx_id}/owner-funds`; вывод проекта разрешает связи только для доходов, расходов и распределения дохода.
- `backend/incoming_invoice_service.py:get_counterparty_balances()`: дебиторка сейчас агрегируется из `Income`, кредиторка — из `IncomingInvoice`.
- `backend/finance_service.py`: P&L и cash-метрики доходов/расходов вычисляются через `Income` и `Expense`; заём не должен попасть в эти выборки.
- `backend/link_diagnostics.py`: список допустимых `matched_type` фиксированный и должен быть расширен новым целевым типом.
- `frontend/src/pages/BankTransactions.jsx`: в модальном окне банка уже есть действия для `owner_funds`, подходящие как шаблон интерфейса.
- `frontend/src/pages/CounterpartyBalance.jsx`: экран показывает только суммарную дебиторку, кредиторку и нетто-баланс; займы нужно раскрыть отдельно.
- После миграции `v18_expense_items` следующую миграцию именовать `v19_counterparty_loans`.

## Модель данных

### `CounterpartyLoan`

Добавить модель в `backend/models.py`:

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| `id` | PK | Идентификатор займа |
| `loan_type` | `borrowed` / `issued`, index | Полученный или выданный заём |
| `client_id` | FK `clients.id`, nullable, index | Существующая карточка контрагента, если выбрана |
| `counterparty_name` | `String(200)`, not null | Имя для незаведённого контрагента и снимок названия |
| `agreement_number` | `String(100)`, nullable | Номер договора займа |
| `agreement_date` | `Date`, nullable | Дата договора |
| `start_date` | `Date`, not null, index | Дата открытия займа |
| `due_date` | `Date`, nullable | Дата возврата по договору |
| `currency` | `String(5)`, default `RSD` | Валюта займа |
| `note` | `Text`, nullable | Примечание |
| `status` | `open` / `repaid` / `cancelled`, index | Статус карточки |
| `created_at`, `created_by` | стандартные поля | Аудит создания |

Не хранить редактируемый «текущий остаток» как источник истины. Рассчитывать его из движений; допустимо вернуть агрегированное значение в API.

### `CounterpartyLoanMovement`

Добавить журнал движений:

| Поле | Тип / ограничение | Назначение |
| --- | --- | --- |
| `id` | PK | Цель связи из `BankTransaction.matched_id` |
| `loan_id` | FK `counterparty_loans.id`, not null, index | Карточка займа |
| `movement_type` | `disbursement` / `repayment`, index | Получение/выдача тела или возврат |
| `date` | `Date`, not null, index | Дата движения |
| `amount` | `Numeric(14, 2)`, `> 0` | Положительная сумма движения |
| `currency` | `String(5)`, default `RSD` | Валюта, должна совпадать с займом |
| `bank_transaction_id` | FK `bank_transactions.id`, nullable, unique | Строка банка, породившая движение |
| `note` | `Text`, nullable | Пояснение |
| `created_at`, `created_by` | стандартные поля | Аудит создания |

В MVP движения создаются только из банка. Поле `bank_transaction_id` оставить nullable, чтобы позднее поддержать ручной начальный остаток или кассу без изменения схемы.

### Константы

В сервисном слое использовать явные константы:

```python
LOAN_TYPE_BORROWED = "borrowed"
LOAN_TYPE_ISSUED = "issued"
LOAN_MOVEMENT_DISBURSEMENT = "disbursement"
LOAN_MOVEMENT_REPAYMENT = "repayment"
MATCH_TYPE_LOAN_MOVEMENT = "loan_movement"
```

## Правила валидации

1. Банковская операция должна быть `unmatched` или `ignored`; привязка уже сопоставленной операции запрещена до явного снятия связи.
2. Для `borrowed/disbursement` разрешён только входящий платёж; для `borrowed/repayment` — только исходящий.
3. Для `issued/disbursement` разрешён только исходящий платёж; для `issued/repayment` — только входящий.
4. Сумма движения берётся из банковской операции, не вводится пользователем повторно.
5. Валюта движения должна совпадать с валютой карточки займа.
6. Возврат не может превышать открытый остаток займа. Переплаты в MVP отклоняются с понятной ошибкой.
7. К закрытому или отменённому займу нельзя добавлять движения; полностью погашенный заём автоматически получает `status = "repaid"`.
8. К займу не назначать проект: principal не является доходом или расходом проекта, а `BankTransaction.project_id` для `loan_movement` должен быть `None`.
9. Удаление или отвязка первоначального транша запрещается, если после неё возвраты превысят оставшиеся выдачи/получения.

## Backend

### Миграция данных

Создать:

- `backend/scripts/migrate_v19_counterparty_loans.py`;
- `manual_migrations/v19_counterparty_loans.cmd`.

Миграция должна:

- создать таблицы `counterparty_loans` и `counterparty_loan_movements`;
- добавить индексы по типу, статусу, датам, `client_id`, `loan_id`;
- добавить уникальный индекс на ненулевой `bank_transaction_id`;
- поддерживать `--dry-run` по шаблону `migrate_v18_expense_items.py`;
- не преобразовывать существующие `owner_funds`, доходы или расходы автоматически: по данным банка нельзя надёжно отличить заём от вложения владельца без решения пользователя.

### Схемы и сервис

Добавить Pydantic-схемы в `backend/schemas.py`:

- создание и редактирование карточки займа;
- создание движения из банковской операции;
- detail response с движениями и рассчитанным `outstanding_amount`;
- list response с фильтрами по типу, статусу и контрагенту;
- поля займов в `CounterpartyBalanceItem` и итогах;
- комментарий `loan_movement` в перечне `BankTransaction.matched_type`.

Создать `backend/counterparty_loan_service.py` с единственным каноническим путём записи:

- `create_loan_from_bank_transaction(...)`;
- `add_movement_from_bank_transaction(...)`;
- `get_loan_outstanding_amount(...)`;
- `reconcile_loan_status(...)`;
- `unmatch_loan_movement(...)`;
- агрегирование задолженности для расчётов с контрагентами.

Сервис должен атомарно создать движение и обновить банковскую строку:

```python
tx.status = "matched"
tx.matched_type = MATCH_TYPE_LOAN_MOVEMENT
tx.matched_id = movement.id
tx.project_id = None
```

### API

Создать `backend/routers/counterparty_loans_router.py`, подключить router в `backend/main.py`:

| Endpoint | Назначение |
| --- | --- |
| `GET /counterparty-loans` | Список займов с фильтрами |
| `GET /counterparty-loans/{id}` | Карточка, движения, остаток |
| `POST /counterparty-loans/from-bank/{tx_id}` | Создать новый заём и первый транш из строки банка |
| `POST /counterparty-loans/{id}/movements/from-bank/{tx_id}` | Добавить транш или возврат к существующему займу |
| `PATCH /counterparty-loans/{id}` | Редактировать договорные сведения, не движения |
| `POST /counterparty-loans/{id}/cancel` | Отменить только карточку без действующих движений |

Payload создания из банка должен содержать тип займа, необязательную карточку клиента, данные договора и примечание. Сумма, дата, направление и валюта берутся с сервера из `BankTransaction`.

### Сопоставление банковских операций

Изменить:

- `backend/bank_matching_service.py`: добавить `MATCH_TYPE_LOAN_MOVEMENT`; обработать `unmatch_transaction()` через сервис займа.
- `backend/routers/bank_transactions_router.py`: сериализовать краткую информацию о связанном займе для модального окна; для `loan_movement` всегда возвращать `project_id = None`.
- `backend/link_diagnostics.py`: включить `loan_movement` в `BANK_MATCH_TYPES_WITH_TARGET`, загрузить движения и проверять наличие движения, уникальность банковской ссылки и совпадение `movement.bank_transaction_id` с самой строкой.

При снятии связи с банковской строки удалить только движение, созданное этой строкой, пересчитать остаток и статус карточки. Саму карточку займа автоматически не удалять, чтобы договор и история исправлений не исчезали.

В MVP не добавлять автоматическое преобразование ошибочного `Expense` или `Income` в заём. Пользователь сначала снимает ошибочную связь, затем оформляет заём. Это уменьшает риск удаления связанных документов; оптимизацию можно добавить позже по образцу проверки `owner_funds`.

### Расчёты с контрагентами

Расширить `get_counterparty_balances()` в `backend/incoming_invoice_service.py` либо вынести общий агрегатор в отдельный сервис. Для каждого контрагента вернуть отдельные составляющие:

```text
document_receivables   # существующий Income
issued_loans           # outstanding по issued
receivables            # document_receivables + issued_loans
document_payables      # существующий IncomingInvoice
borrowed_loans         # outstanding по borrowed
payables               # document_payables + borrowed_loans
net_balance            # receivables - payables
```

Так займы войдут в общий расчёт задолженности, но останутся различимыми от фактур.

### Отчётность

Проверить `backend/finance_service.py` и связанные endpoints:

- `loan_movement` не должен добавляться в выборки выручки, дохода, расхода, налоговой базы или P&L;
- физическое движение по банку должно оставаться видимым в банковском журнале;
- если экран cash flow показывает только операционные доходы/расходы, добавить отдельный раздел или тип «Финансирование: займы», а не подмешивать principal в revenue/expense.

Отдельный PDF для займа не нужен в MVP: договор займа является внешним документом. Экспорт карточки/реестра движений можно реализовать последующим этапом.

В карточке несопоставленной операции добавить действия, зависящие от направления:

| Направление | Кнопки займа |
| --- | --- |
| Входящая операция | `Получить заём` и `Возврат выданного займа` |
| Исходящая операция | `Выдать заём` и `Погасить полученный заём` |

Не объединять эти действия с кнопкой «Внести собственные средства». Разместить их рядом в группе недоходных/нерасходных операций, сохранив смысл:

- «Собственные средства» — деньги владельца;
- «Займы» — долг с конкретным контрагентом и контролируемым остатком.

Диалог займа должен:

- для первого транша позволять выбрать `Полученный` / `Выданный`, контрагента и сведения договора;

- показывать сумму банковской операции read-only;
- показывать остаток до и после операции;
- не предлагать проект или категорию дохода/расхода.

Для связанной строки показывать статус вида:

- `Связано (Получение займа)`;
- `Связано (Возврат займа)`;
- ссылку `Открыть заём`;
- действие `Отвязать`, использующее существующий workflow банка.

## Проверки

### Миграция и backend

Запустить:

```powershell
.\venv\Scripts\python.exe backend\scripts\migrate_v19_counterparty_loans.py --dry-run
.\venv\Scripts\python.exe -m compileall backend
```

Проверить вручную или автоматизированными тестами:

1. Входящую операцию `350000 RSD` оформить как `borrowed/disbursement`: создаётся открытый заём с кредиторкой `350000`, но нет нового `Income`.
2. Исходящую операцию `100000 RSD` оформить как возврат этого займа: остаток `250000`, но нет нового `Expense`.
3. Исходящую операцию оформить как выдачу займа: появляется дебиторка, не расход.
4. Входящую операцию оформить как возврат выданного займа: дебиторка уменьшается, не доход.
5. Частичный возврат разрешён; возврат больше остатка отклоняется.
6. Неверное направление операции отклоняется для каждого типа движения.
7. Полный возврат переводит заём в `repaid`.
8. Отвязка движения возвращает банковскую строку в `unmatched` и корректно пересчитывает долг.
9. Отвязка, создающая отрицательный остаток из-за последующих возвратов, запрещается.
10. `link_diagnostics.py` не выдаёт ошибок для корректных `loan_movement` и обнаруживает потерянные связи.

cmd /c npm --prefix frontend run build

4. На странице займов видны транши, возвраты и остаток.
5. В «Расчётах с контрагентами» заём отражается отдельными колонками и входит в итог.
6. На рабочем разрешении modal и таблица не требуют горизонтальной прокрутки для типового займа.
7. P&L и операционные доходы/расходы не изменяются после оформления тела займа.

## Критерии приёмки

- Пользователь может оформить показанное поступление `+350 000 RSD` как полученный заём от организации.
- Можно вести как полученные, так и выданные займы, включая частичные возвраты.
- Остаток долга вычисляется только из движений и не редактируется вручную.
- Тело займа не создаёт записи дохода или расхода и не меняет P&L.
- Банковская операция имеет проверяемую связь с конкретным движением займа.
- Займы видны отдельно в расчётах с контрагентами и в собственном реестре.
- Ошибочную связь можно безопасно снять без потери согласованности данных.

## Не включать в MVP

- автоматическое начисление процентов и штрафов;
- валютную переоценку;
- взаимозачёт займа с фактурами;
- кассовые движения по займу;
- автоматическое распознавание займа из назначения платежа;
- массовое преобразование ранее отмеченных собственных средств, доходов или расходов;
- формирование договора займа или бухгалтерского PDF-документа.
